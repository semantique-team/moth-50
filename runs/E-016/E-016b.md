# E-016b — segmentation default (adopted: split at three or more runs)

> **Status: adopted 2026-11-23 (D29, post-hoc).** The runtime now splits a clip
> that fits one 30 s segment only when the VAD finds **three or more speech
> runs** (two or more for longer recordings). On S1-dev the browser default
> moves from **14.0979 %** to **13.7180 %** WER, a tie with the Python readout
> (+0.3360 pp [−0.1312, +0.7948], ETA +0.49 pp tie). Multi-sentence diagnostics
> with 5–6 runs keep the old segmented behaviour. The model package is
> unchanged; this is a web-runtime rule only.

## Why

E-016 measured the browser default at **+0.7159 pp** WER vs Python on S1-dev
(CI excludes zero), while `segment: false` was a tie (+0.3506 pp). The default
splits at every VAD run pair; on a short single-sentence clip with an internal
pause this removes context. The runtime comment already warned that cutting a
single run removes the leading silence the model expects, and that five
concatenated sentences read as one stream cost 9.4 WER points. The rule must
therefore keep multi-sentence splitting.

## Rule

```js
const minimumRuns = pcm.length > maxSamples ? 2 : 3;
const spans = bounds.length >= minimumRuns ? bounds : [{ start: 0, end: pcm.length }];
```

- A clip that fits one 30 s segment: full-clip decoding with **two** runs (one
  utterance with a pause), segmented with **three or more**.
- A longer recording: segmented at two or more runs, so every span fits the
  model (the 35 s smoke below gives 8 spans).
- An explicit `segment: true/false` still overrides.

The diff is `vendor/moth-stt-web/PATCH-2026-11-23.diff`; the patched `ort.js`
sha256 is `96d099b5…`. All other vendored files remain byte-identical to
upstream `0e15442`.

## Evidence

**S1-dev (960 clips, 6,845 ref words), browser vs the Python readout
13.3820 % / 75.1465 %:**

| Browser rule | WER | ETA | vs Python WER (95 % CI) | Tie |
|---|---:|---:|---|---|
| upstream default (2+ runs) | 14.0979 | 75.5859 | +0.7159 pp [+0.1678, +1.2599] | no |
| `segment: false` | 13.7327 | 75.5859 | +0.3506 pp [−0.1255, +0.8160] | yes |
| **min runs 3** | **13.7180** | **75.6348** | **+0.3360 pp [−0.1312, +0.7948]** | **yes** |

The rule is almost exactly the full-clip result while keeping segmentation for
the multi-sentence case. By VAD run count on S1-dev: 882 clips have one run
(identical under every rule), 73 have two runs (upstream 15.60 % vs full
13.21 %), 5 have three or four (upstream 11.31 % vs full 11.90 %). The rule
takes the better side of each group.

**Multi-sentence concatenations (0.4 s silence between clips):**

| Set | Clips | Duration | Upstream segment | Full clip | min runs 3 |
|---|---:|---:|---:|---:|---:|
| MLS-IT dev, 100 groups | 200 | 21.4–28.4 s | 20.672 | **18.572** (−2.10 pp [−3.36, −0.93]) | 20.672 |
| T-600, 100 groups (diagnostic only) | 500 | 10.5–17.7 s | 12.125 | 14.261 (+2.14 pp [+0.77, +3.49]) | **12.125** |
| Gold train, 100 groups | 500 | 12.3–20.6 s | 0.484 | 0.588 (tie) | — |

- The T-600 concatenation is **diagnostic only**: T is the evaluation set and
  was not used to select the rule. It shows why a blanket auto-off is unsafe:
  five short sentences fit 30 s but read better when segmented.
- The gold-train concatenation is not discriminative: the model has seen the
  sentences and both variants are near zero.
- MLS-IT dev is a legitimate training-side/dev diagnostic. Full-clip decoding
  is better there (two long utterances, 3+ VAD runs because of internal
  pauses), so min-runs-3 does **not** capture that gain. It also does not
  regress it: 20.672 either way. A future rule that decides by utterance
  length or a two-pass score could, but it is out of scope here.
- **35 s smoke:** a 35 s clip with eight pauses transcribes with
  `segments: 8`, no error; the >30 s path is intact.

The original E-016b wording ("auto-disable segmentation when the clip fits one
30 s segment") is **rejected**: it removes segmentation from every multi-
sentence clip under 30 s and loses 2.14 pp on the five-sentence diagnostic. The
adopted rule is the narrower min-runs-3 variant, labelled post-hoc in D29.

## Reproduce

```bash
npm ci --prefix vendor/moth-stt-web
python tools/serve_web.py --release runs/E-023/release-0.9.7 \
  --mount dataset=../moth-cs-dataset --port 8790
node tools/browser_probe.mjs s1dev --base-url http://127.0.0.1:8790 \
  --threads 4 --manifest /dataset/manifests/R-S1-dev.jsonl \
  --audio-base /dataset/ --out runs/E-016/s1-dev-browser-minruns3.json
uv run --frozen --project ../moth-stt --extra training -- \
  python tools/browser_parity.py \
  --manifest ../moth-cs-dataset/manifests/R-S1-dev.jsonl \
  --reference-hyp runs/E-023/s1-dev-s0.hyp.jsonl \
  --browser runs/E-016/s1-dev-browser-minruns3.json \
  --out runs/E-016/browser-vs-python-minruns3.json
```

The concatenated diagnostics are built from the source manifests with 0.4 s of
silence between clips; the source ids and the per-variant metrics are in
`e016b-diagnostics.json`. The T-600 concatenation is retained only as the
negative diagnostic; it is not a selection set.
